# Plan: run ProxCenter as a guest

**Status:** deployed on 2026-11-09 to vmid 125, group `pc`. Measured on the
guest: first run 26 changed, second run failed on a templating bug and a
directory-ownership bug (both fixed, see §10), third run **0 changed, 0 failed**,
67 tasks, 60 s. The UI answers on `10.0.0.82:3000`; `/api/health` returns
`{"status":"healthy","db":"reachable"}`.

**Scope:** one new application role `apps/proxcenter/`, one `app.yaml` entry,
one guest in `inventory/`. Nothing in `common/` and nothing in `playbooks/`
changes.

**Decisions as built**, differing from the draft where the operator chose
otherwise:

| | Draft | Built |
|---|---|---|
| D4 size | 4 / 8192 / 80 | **2 / 4096 / 40** (upstream "Small") |
| D5 onboot | framework default 0 | **1** |
| D6 token | operator creates it | **created here**: `proxcenter@pve`, `PVEAdmin` at `/`, token `proxcenter@pve!proxcenter` with `privsep 0` |
| D3 firewall | ufw | **DOCKER-USER** rule, `10.0.0.0/8` |

ProxCenter is a **Next.js application plus PostgreSQL, shipped as a Docker
Compose stack**. That makes it the fourth kind of application this repository
handles, and the first that is neither a wheel nor a single binary:

| Application | What the role installs |
|---|---|
| `example-app` | a wheel, from PyPI |
| `omniroute-release` | an npm release, as files plus a systemd unit |
| `xerj` | one pinned binary, as a systemd unit |
| `builder` | a toolchain, and nothing that listens |
| **`proxcenter`** | **a Docker engine, two images, and a Compose stack** |

The framework has no opinion about Docker. The role therefore owns: installing
the engine, pinning two images by digest, writing the Compose project,
creating the external volumes, and proving the stack answers. The stack
itself remains the vendor's file, fetched from upstream and checksum-verified,
with one small override file of ours on top.

## 1. Decisions this plan needs from you

Six. Four are cheap to reverse; two are not.

### D1 — Which route: a DeployFlow role, or the vendor's installer by hand?

| | A. DeployFlow role | B. Vendor installer by hand |
|---|---|---|
| What it is | `apps/proxcenter/` + one manifest entry + one inventory host | `pct create`, then `curl … install-community.sh \| sudo bash` on the guest |
| Reproducible | yes — the stack is pinned by digest and the Compose file by sha256 | no — the vendor script writes `VERSION=latest` and fetches a moving tag |
| Secrets | in this repository's `.env`, never on a command line | generated by the script, on the guest, and not visible to `appctl` |
| Idempotence | `changed=0` on a second run is a real criterion | none — the script is "run it again and hope" |
| Cost | one afternoon of role work | twenty minutes |

**Decided: A.** B is the right answer for a throwaway evaluation, and the plan
keeps it as §7 so it can be tried first. A is the right answer for something
that will hold Proxmox API credentials and a management database: the vendor's
installer fetches `docker-compose.community.yml` from a **branch** URL
(`…/main/docker-compose.community.yml`), so the file that runs on the guest is
whatever upstream had that minute, and it pins `VERSION=latest`, so the image
is whatever was built last. Two of this repository's standing rules are about
exactly this: a role pins what it installs, and a green play must not be able
to hide a broken service.

The route does not have to be all-or-nothing: **do B first, on a throwaway
guest, to see the product** (§7), then decide whether to keep it or replace it
with A.

### D2 — Which build of the image?

The published image, pinned by digest. Measured:

```
ghcr.io/adminsyspro/proxcenter-frontend:latest
  digest sha256:0ff8006e3ab9b4f8143e3e8fd89ba3067b89d69a7fbf4ac835600e07785ad3de
  amd64 only, 20 layers, 265 MB compressed
```

The same digest is published under `1.4.14` (the version in
`frontend/package.json`) and under `latest`, and the registry also carries
`sha-<commit>` tags. The local checkout at
`/home/bruj0/projects/proxcenter-ui` is at `ff87fe01`, which is **the same
commit as upstream** — verified against
`github.com/adminsyspro/proxcenter-ui` — so there is no fork divergence to
honour and no reason to build locally.

**Decided: the published image, pinned by digest.** A local build is possible
(the controller is x86_64 with Docker 29.9.3, and the Dockerfile is a
three-stage build), but it would give this repository a build pipeline for a
product it does not own, and the digest of the published image is the same
contract as the digest of XERJ's release archive.

### D3 — Exposure. The one that actually costs something.

ProxCenter holds a **Proxmox API token** and, in the hands of its
administrators, the ability to read and change every guest on this host. It is
the most privileged thing on this network after the Proxmox host itself.

| | Bind | Cost |
|---|---|---|
| **A** | `127.0.0.1` on the guest | Unreachable. Only useful behind an SSH tunnel, and a browser does not survive one. |
| **B** | `0.0.0.0:3000` on the guest's `vnet0` address | LAN-reachable over plain HTTP. The first-run setup endpoint is unauthenticated until an admin exists, so `PROXCENTER_SETUP_TOKEN` must be set. |
| **C** | `0.0.0.0:3000` behind a reverse proxy on another host, with TLS | The right end state. Not free: it needs a hostname and a certificate. |

**Decided: B, with `PROXCENTER_SETUP_TOKEN` set, and a DNS record as the
handle.** The upstream installer publishes 80 and 443 with a **self-signed**
certificate, which teaches every browser on the network to distrust this host
for that name; port 3000 in plain HTTP is the smaller, reversible thing.

The handle is a DNS A record: `proxcenter.intranet.local` in the existing
`intranet.local` zone, pointing at the guest's leased address. The guest's
address is a DHCP lease and can change; a hostname does not.

**This is where a trap lives, and it is not a small one.** The guest's firewall
is `ufw`, and **`ufw` does not filter a Docker-published port**. Docker
installs its own `DOCKER` chain in `nat`/`filter`, which is evaluated before
`ufw`'s `INPUT` chain. A rule that denies 3000 to the world and allows it to
one subnet will be **reported as applied by `ufw status` and enforced by
nothing.** Measured on the one container on this host that runs Docker
(vmid 107): `ufw status` reports `inactive`, `iptables -S DOCKER-USER` is
empty, and published ports are reachable regardless. So the `xerj`-style
"apply a firewall and prove it" pattern does **not** transfer here. The
restriction has to be a `DOCKER-USER` rule, or the Proxmox firewall, or the
network itself.

### D4 — Size.

Upstream's own matrix, for a ProxCenter instance that manages this cluster:

| Infrastructure | vCPU | RAM | Disk |
|---|---|---|---|
| Small (≤50 nodes, ≤1500 guests) | 2 | 4 GB | 40 GB |
| Medium (≤150 nodes, ≤4500 guests) | 4 | 8 GB | 80 GB |

**Decided: 4 cores / 8 GB / 80 GB**, on `data1` (1.27 TiB free). This is
upstream's "Medium" row, not a measurement of this deployment. The host has
12 cores and 125 GB of RAM, 96 GB available, so the guest is a third of the
machine's memory — sized for the database and the metrics history, not for the
dashboard.

Disk grows with metrics history: upstream states about 90 MB per node at the
default 14-day retention. With one node here that is noise; the 80 GB is
headroom for the Docker image layers, the database and the upgrades.

### D5 — VMID.

**Decided: 125.** Taken on this host: 100–124 and 200. Free: 125 and
anything above 200.

### D6 — Which Proxmox API token?

ProxCenter authenticates to PVE with an API token
(`frontend/src/lib/connections/getConnection.ts` decrypts `apiTokenEnc`; the
token is entered in the UI on first setup). The token's privileges become
ProxCenter's privileges.

**Decided: a dedicated token, scoped to the least it can do, and stored in
this repository's `.env` as `proxcenter_pve_token`.** It is created on the
Proxmox host, and it is a credential this repository will hold — so it is a
declared secret (`app.yaml`'s `secrets:` list), never a value in a role
default.

The scoping itself is a separate decision the operator makes when the token is
created, and the plan does not pre-empt it: `PVEAuditor` (read-only) is enough
for inventory and dashboards; `PVEPowerUser` is what the guest-management
features need. **Create it read-only first**, look at what the product
actually refuses to do, and widen it deliberately.

## 2. What gets created

```
apps/proxcenter/
  defaults/main.yml       the interface: name, port, versions, digests, paths
  meta/main.yml           dependencies: [role: python]
  tasks/main.yml          install Docker, fetch the Compose file, pin the
                          images, write .env, create the volumes, up, prove
  templates/
    proxcenter.env.j2     the stack's .env — the only file holding secrets
    proxcenter-compose.override.j2
                          our overlay: digest-pinned images and bind mounts
```

Plus, outside the role:

- one block in `app.yaml` (`applications.proxcenter`);
- one host in `inventory/hosts.yml` under `lxc:`;
- one group `pc` in `inventory/hosts.yml`;
- `inventory/group_vars/pc/main.yml` with `app_roles: [proxcenter]` and the
  size overrides from D4.

`inventory/` and `app.yaml` are gitignored; only the role and this plan are a
commit.

**Two things about the role's shape are worth stating before the code.**

**It depends on `common/python`, and the venv it installs is inert.** That
dependency is what asserts `app_port` is defined and what creates
`app_user`, `app_home`, `app_dir` and `app_state_dir`. ProxCenter uses none
of the Python. `omniroute-release` and `xerj` pay the same cost for the same
reason, and the alternative — an application that installs a service and
defines its own account — duplicates what the framework already owns.

**It does not depend on `common/lxc`.** The guest is created by play 1 of
`playbooks/site.yml`, which every host in the `lxc:` group gets. The role only
runs on the guest.

## 3. The manifest entry

```yaml
proxcenter:
  description: the ProxCenter management plane, from pinned container images
  target:
    kind: proxmox_lxc
    options:
      hostname: proxcenter
      vmid: 125
      bind_host: 0.0.0.0        # D3=B. 127.0.0.1 for D3=A.
  source:
    kind: package
    # The `package` kind is a stretch, deliberately, and it is the same
    # stretch `omniroute-release` makes for an npm release: the schema has
    # three kinds and this is the one that says "a released artifact pinned
    # by version". The `==` form is what makes appctl pass the pin into the
    # play as appctl_source_package / appctl_source_version, so the role can
    # refuse a version the manifest did not name.
    package: "proxcenter==1.4.14"
  secrets:
    - proxcenter_pve_token
```

**No `config` block.** `appctl render` emits exactly one JSON document and
the framework copies one file; ProxCenter's configuration is a `.env` file
with a dozen keys and a Compose project beside it. The role writes both, the
way `omniroute-release` writes its env files. A `config` block here would
produce a JSON file nothing reads.

**Exactly one secret is declared, and the reason is the framework's.**
`appctl` requires every name in `secrets:` to be present in `.env` before it
will start a play — `appctl secrets check` refuses the install otherwise. A
secret the role generates itself therefore **cannot** be in that list.

So the five credentials split by origin:

| Credential | Origin | Where it lives |
|---|---|---|
| `proxcenter_pve_token` | the operator, created on the Proxmox host | `.env` here, then the guest |
| `APP_SECRET` | generated by the role, once | the guest's stack `.env` |
| `NEXTAUTH_SECRET` | generated by the role, once | the guest's stack `.env` |
| `POSTGRES_PASSWORD` | generated by the role, once | the guest's stack `.env` |
| `PROXCENTER_SETUP_TOKEN` | generated by the role, once | the guest's stack `.env` |

The four generated ones must be **stable across reinstalls**. A regenerated
`POSTGRES_PASSWORD` makes the database refuse its own new password; a
regenerated `APP_SECRET` makes ProxCenter unable to decrypt the stored
Proxmox token — silently, and with the symptom "the connection I saved has
stopped working" rather than "the install failed". The role reads the
existing `.env` first and keeps every value it finds.

## 4. The role

### `defaults/main.yml`

```yaml
app_name: proxcenter
app_service_name: proxcenter

# The port the stack publishes. The upstream Compose file maps
# "${HTTP_BIND:-3000}:3000", and the vendor installer overrides HTTP_BIND to
# 80 on a fresh install. This role keeps 3000 (see D3).
app_port: 3000

# ---------------------------------------------------------------------------
# The upstream artifacts
# ---------------------------------------------------------------------------
# The Compose file is fetched from upstream at a commit URL, not from a branch
# URL. The vendor installer uses .../main/docker-compose.community.yml, which
# means the file that runs on the guest is whatever upstream had that minute.
# The sha256 below is of that exact file at that exact commit, measured on
# 2026-11-09.
proxcenter_upstream_commit: "ff87fe01fb936b856ba158b79e767f8d251433ae"
proxcenter_compose_url: >-
  https://raw.githubusercontent.com/adminsyspro/proxcenter-ui/{{ proxcenter_upstream_commit }}/docker-compose.community.yml
proxcenter_compose_sha256: "1993a8dbce576ee73ff1df55d1d3cf6143816acea8646f61248b0d40bd291852"

# The images
# ---------------------------------------------------------------------------
# Both pinned by digest. A tag is a moving name; the digest is the thing.

# anonymous pull token — the image is public, so the guest needs no

proxcenter_frontend_image: >-

proxcenter_frontend_version: "1.4.14"

proxcenter_postgres_image: >-
  postgres@sha256:aa6cb33cf4c19c765cefcf48d96176258800870a9a1e930ad126200f9d825139

# ---------------------------------------------------------------------------
# The engine
# ---------------------------------------------------------------------------
# Docker CE from Docker's own apt repository. Measured on 2026-11-09: the
# `resolute` distribution (Ubuntu 26.04) carries docker-ce 29.4.0 and
# docker-compose-plugin 5.1.0, so the guest's stock template is supported.
# Pinning the version is optional and deliberately left unpinned here: the
# engine is not the thing being deployed, and a pinned engine that apt no
# longer carries is a worse failure than a patched one.
proxcenter_docker_apt_key_url: "https://download.docker.com/linux/ubuntu/gpg"
proxcenter_docker_apt_repo: "https://download.docker.com/linux/ubuntu"
proxcenter_docker_packages:
  - docker-ce
  - docker-ce-cli
  - containerd.io
  - docker-buildx-plugin
  - docker-compose-plugin

# ---------------------------------------------------------------------------
# Paths
# ---------------------------------------------------------------------------
# The Compose project. app_state_dir holds the mutable data; app_dir holds
# the project files. A reinstall replaces the project and leaves the data.
proxcenter_project_dir: "{{ app_dir }}/project"
proxcenter_env_file: "{{ proxcenter_project_dir }}/.env"
proxcenter_compose_file: "{{ proxcenter_project_dir }}/docker-compose.yml"
proxcenter_compose_override: "{{ proxcenter_project_dir }}/docker-compose.override.yml"

# volumes (see §5, "Persistence").

proxcenter_postgres_dir: "{{ app_state_dir }}/postgres"

# ---------------------------------------------------------------------------

# ---------------------------------------------------------------------------

proxcenter_bind_host: "0.0.0.0"
```

**Two naming notes that are load-bearing, and both are traps this repository
has already paid for.**

`proxcenter_bind_host`, **not** `app_bind_host`. `common/python` defines
`app_bind_host: 127.0.0.1`, and a meta-dependency's defaults are applied
**after** the including role's — so a role that sets `app_bind_host: 0.0.0.0`
is silently given the framework's loopback value and the service is
unreachable with nothing in the log to say why. This is the same trap
`apps/xerj` documents, and it is why XERJ's variable has its own name.

`proxcenter_project_dir` under `app_dir`, data under `app_state_dir`. The
framework's contract is that `app_dir` is replaced and `app_state_dir` is
never touched. A database inside `app_dir` would be deleted by the next
install.

### `meta/main.yml`

```yaml
dependencies:
  - role: python
```

### `tasks/main.yml`, in order

1. **Assert the manifest's pin matches the role's.**
   `appctl_source_package == 'proxcenter'` and
   `appctl_source_version == proxcenter_frontend_version`. The manifest and
   the role each name a version, and two files that can disagree is exactly
   how `omniroute-release` ended up pinned to 3.8.51 while the manifest said
   3.8.53. Failing here costs a task; failing later costs an operator
   wondering which one was reviewed.

2. **Assert the guest can host Docker.** Memory, cores and free space on `/`.
   A guest that is too small does not fail at install — it fails hours later,
   during a build, with an error that names a memory limit rather than the
   guest. Same reasoning as `apps/builder`'s assertions.

3. **Install the Docker engine.**
   The apt key to `/etc/apt/keyrings/docker.asc`, the repo for the guest's
   own codename (`lsb_release -cs` → `resolute` on Ubuntu 26.04), then the
   packages from `proxcenter_docker_packages`. Then `systemctl enable --now
   docker`.

   The role must **not** copy the vendor's `install-community.sh` step for
   step, because that script also removes `docker`, `containerd` and `runc`
   before installing them — a destructive line that is fine on a fresh host
   and wrong on a guest that already has a container runtime. The role
   installs; it does not uninstall.

4. **Fetch the Compose file and verify it.**
   `get_url` with `checksum: "sha256:{{ proxcenter_compose_sha256 }}"`. The
   checksum is what makes the download idempotent: `get_url` skips the
   transfer when the file on disk already matches, so a second run reports
   unchanged. **A `get_url` without a checksum re-downloads on every play
   and reports changed** — this is the most common way a role stops being
   `changed=0`.

5. **Write the override file** (the template above). It pins the images by
   digest and replaces the two named volumes with bind mounts.

6. **Write the stack's `.env`**, mode 0600, owner root. It carries
   `APP_SECRET`, `NEXTAUTH_SECRET`, `POSTGRES_PASSWORD`,
   `PROXCENTER_SETUP_TOKEN`, `NEXTAUTH_URL`, `APP_URL`, `HTTP_BIND`,
   `HTTPS_BIND`, `TLS_ENABLED`, `VERSION`, and the operator's
   `PROXCENTER_PVE_TOKEN` if the role passes it through.

   **The generated secrets are generated once and never regenerated.** The
   role reads the existing `.env` first and keeps any value already present.
   A role that regenerated `POSTGRES_PASSWORD` on every run would break the
   database on the second install, and one that regenerated `APP_SECRET`
   would invalidate every session and every stored credential — with the
   symptom being "the UI logged me out", not "the install failed".

7. **Create the data directories and their ownership.**
   `proxcenter_data_dir` must be writable by **uid 1001** — the frontend
   container's `nextjs` user. The upstream installer does this with a
   `docker run --user root --entrypoint "" -v … sh -c "mkdir -p … && chown -R
   1001:1001 …"`; the role can do the same thing with `file: owner: "1001"`,
   which is cheaper and does not require the image to be pulled first.
   `proxcenter_postgres_dir` is left to the Postgres image's own entrypoint,
   which chowns a bind-mounted `PGDATA` when it is empty.

8. **Pull the images by digest and verify.**
   `docker pull <digest>` for both, then `docker image inspect` to assert the
   digest matches the pin. `changed_when` is set from the pull's own output,
   which reports `Image is up to date` for an image already present.

9. **`docker compose up -d`.** With `--pull never`, so a Compose run cannot
   fetch a different image than the one the role pinned.

10. **The postconditions.** Below.

### Postconditions — the point of the role

A green play that does not prove the stack works is the failure this
repository exists to prevent. The role asserts, after `up`:

- **Both containers are running** — `docker compose ps`, both services
  `running`.
- **The frontend answers.** `GET http://127.0.0.1:{{ app_port }}/api/health`
  returns 200. The upstream compose file's own healthcheck uses exactly this
  path, and `/api/health` is deliberately exempt from the HTTPS redirect, so
  it answers in plain HTTP even with TLS enabled.
- **Postgres is healthy.** `pg_isready -U proxcenter -d proxcenter`, which
  is the compose file's own healthcheck.
- **The database has the schema.** The entrypoint applies Prisma migrations
  and an idempotent seed before the server starts; the role asserts the
  `migrations` table is non-empty, which is what "the migrations ran" looks
  like from outside the container.
- **The published port is reachable from the guest's own address**, not only
  from loopback, when the bind is not loopback. A container that answers on
  127.0.0.1 and is published on `0.0.0.0` is a green play with an
  unreachable service.
- **The published port is reachable from outside the guest**, when the bind
  is not loopback — the controller curls the guest's leased address. This is
  the assertion that catches a `ufw` rule that Docker bypassed (D3).

Each assertion is a separate task with a message that names what failed and
what would prove it. `appctl` prints the role's own "Report the checks that
passed" lines, so the operator reads the application's statement about itself
rather than a task count.

## 5. Persistence, and the one thing that is not solved

**The vendor's Compose file declares its volumes `external: true`:**

```yaml
volumes:
  proxcenter_data:
    name: proxcenter_data
    external: true
  postgres_data:
    name: postgres_data
    external: true
```

`external: true` means Compose will **not** create them. The upstream
installer works around this with two `docker volume create` calls; a role
that forgets them gets `docker compose up` failing with "network/volume not
found", and no service at all.

**The plan replaces them with bind mounts**, via the override file, pointing
at `app_state_dir`:

```yaml
services:
  frontend:
    image: ghcr.io/adminsyspro/proxcenter-frontend@sha256:0ff8…
    volumes:
      - {{ proxcenter_data_dir }}:/app/data
  postgres:
    image: postgres@sha256:aa6c…
    volumes:
      - {{ proxcenter_postgres_dir }}:/var/lib/postgresql/data
volumes:
  proxcenter_data: null
  postgres_data: null
```

Two reasons. First, the data becomes visible on the guest's filesystem, where
a backup is a `tar` and where the operator can see it. Second — and this is
the one that matters — **a Docker named volume lives in `/var/lib/docker` on
the guest's rootfs, so it is destroyed with the guest.** A bind mount under
`app_state_dir` survives an application reinstall; it does not survive a
rebuilt guest, and nothing in this framework makes a rebuilt guest cheap.
See §8.

**The override is a fork of the vendor's file, and that is a cost.** It is
small — two image pins, two volumes — and it is why the upstream file is
fetched rather than copied: the next upgrade changes the upstream file, and
the override's two edits are the only thing that has to be replayed. The
role must apply the override with `docker compose -f docker-compose.yml -f
docker-compose.override.yml` and use **both** `-f` flags everywhere, or the
override is silently ignored and the pinned image is never used — a green
play running the wrong image.

## 6. The two files that hold secrets

### The stack's `.env` on the guest

`{{ proxcenter_project_dir }}/.env`, mode `0600`, owner root. It holds:

```
APP_SECRET=<generated once>
NEXTAUTH_SECRET=<generated once>
POSTGRES_PASSWORD=<generated once>
PROXCENTER_SETUP_TOKEN=<generated once>
NEXTAUTH_URL=http://proxcenter.intranet.local:3000
APP_URL=http://proxcenter.intranet.local:3000
HTTP_BIND=3000
HTTPS_BIND=8443
TLS_ENABLED=false
VERSION=1.4.14
```

`HTTPS_BIND` and `TLS_ENABLED` are set explicitly rather than left to the
vendor's defaults, and this is worth explaining because the vendor's defaults
are deliberate.

The vendor's Compose file maps `"${HTTPS_BIND:-}:${TLS_PORT:-8443}"` — with an
empty `HTTPS_BIND`, Docker publishes the container's 8443 on **a random free
host port**. The vendor's installer comments this at length: an upgrade pulls
the file without ever having asked for TLS, and a hard-coded 8443 on a host
that already uses that port makes the whole stack fail to start. The
consequence for us is that leaving `HTTPS_BIND` empty means the container has
a TLS port on an unpredictable host port. Setting it to `8443` explicitly with
`TLS_ENABLED=false` keeps the mapping deterministic and leaves the container's
plain HTTP on 3000 as the only thing serving traffic.

**The upstream installer sets `HTTP_BIND=80` and `HTTPS_BIND=443` on a fresh
install** with a self-signed certificate. We do not. Port 443 with a
self-signed certificate on a host whose name is in nobody's trust store is a
worse first impression than 3000 in plain HTTP, and it is trivially changed
later.

### The Proxmox API token

`proxcenter_pve_token` is the one secret that comes from outside. It is
declared in `app.yaml`'s `secrets:` list, so `appctl secrets check` refuses
an install without it, and it is delivered the way every secret in this
repository is delivered: in a temporary extra-vars file, mode 0600, never in
`argv`.

It reaches the guest as an environment variable on the Compose project
(`environment:` in the override, or a variable in the `.env`), and ProxCenter
itself never needs it at boot — the token is entered in the UI when the
first connection is created, and ProxCenter encrypts it into its own
database (`apiTokenEnc`, decrypted with `APP_SECRET`). **So the token's
lifetime in the guest is a design choice, not a requirement:** the role can
write it into the stack's `.env` and hand it to the operator for entry in the
UI, and the ProxCenter connection can be created by hand afterwards.

The plan keeps it that way: the token is written to a `0600` file on the
guest, the role prints the path and not the value, and the operator pastes it
into the UI. Nothing in the framework automates the ProxCenter connection,
and pretending otherwise would put a credential into a database through a
path nobody audited.

**One caveat about `APP_SECRET`.** The stack's `.env` holds the value that
encrypts the stored Proxmox token. If the role regenerates `APP_SECRET` on a
reinstall, ProxCenter can no longer decrypt the stored token, and the stored
connection is silently broken. That is the single most expensive thing this
role could get wrong, and it is why "generated once, never regenerated" is a
rule rather than a preference.

## 7. The fast route, if the goal is to see the product first

Before writing a role, twenty minutes on a throwaway guest answers most
questions. This is route B from D1 and it is a real option, not a toy.

```bash
# On the Proxmox host.
pct create 199 local:vztmpl/ubuntu-26.04-standard_26.04-1_amd64.tar.zst \
  --hostname proxcenter-try \
  --arch=amd64 --cores=4 --memory=8192 --swap=1024 \
  --rootfs=data1:80 \
  --net0=name=eth0,bridge=vnet0,ip=dhcp,type=veth \
  --unprivileged=1 --features=nesting=1,fuse=1,keyctl=1 --onboot=0 --start=1
```

Then, inside the guest:

```bash
curl -fsSL https://proxcenter.io/install/community | sudo bash
```

and open `http://<guest-address>:3000`.

**What this route does not tell you**, and why the role is still worth
writing afterwards:

- it fetches the Compose file from a **branch** URL and pins `VERSION=latest`,
  so the stack that ends up running is not the stack anyone reviewed;
- it generates its own secrets on the guest, so there is no record of them
  anywhere and no way to migrate them into the role's `app_state_dir`;
- it publishes 80 and 443 with a self-signed certificate;
- it has no idempotence, so "run it again" is not a defined operation;
- the data lands in Docker named volumes and is lost with the guest.

If the evaluation is worth keeping, the migration is mechanical: the roles
in §4 read the existing `.env` and keep every value it finds, so the
generated secrets survive the switch, and the data moves from the named
volumes into the bind mounts with a `docker run` copy.

**Do not use VMID 199** — it is not free on this host, where 100–124 and 200
are taken. Use **125**, the number D5 reserves, even for the evaluation: if
the evaluation becomes the deployment, the guest does not have to be rebuilt
to change its identity, and a rebuilt guest loses the bind-mounted data.

## 8. What this deliberately does not do

- **It does not build the image.** D2. The published image, pinned by digest.
- **It does not run the vendor's installer.** D1. The installer fetches a
  moving branch URL and generates secrets it keeps nowhere.
- **It does not deploy the Enterprise edition.** The Community compose file
  is the one with two services. Enterprise adds an orchestrator, a WeasyPrint
  sidecar and a licence key; the sidecar image
  `ghcr.io/adminsyspro/proxcenter-weasyprint` returned **403** to an
  anonymous pull token on 2026-11-09, so it is not publicly pullable and
  this plan does not cover it.
- **It does not put a reverse proxy in front.** D3 stops at option B. A
  reverse proxy on another host with a real certificate is the follow-up, and
  ProxCenter has a "Behind reverse proxy" toggle for exactly that case.
- **It does not configure a backup.** The database is a bind mount under
  `app_state_dir`, which is what makes a backup possible; the backup itself
  is a separate decision.
- **It does not create the Proxmox API token.** D6. The operator creates it,
  with the privileges the operator wants, and the role only refuses to
  install without it.
- **It does not survive a rebuilt guest.** The bind mounts live on the
  guest's own rootfs. `pct destroy` takes the database with it. This
  framework has no host-side storage for guest state, and inventing one is a
  change to `common/lxc` that this plan does not propose.

## 9. Acceptance

```bash
appctl install proxcenter      # first run: several changed
appctl install proxcenter      # second run: MUST be changed=0
appctl list                    # DEPLOYED shows proxcenter
```

Then the three drifts that actually happen, and one re-run that repairs them:

```bash
# On the guest.
rm -f /opt/proxcenter/app/project/docker-compose.yml
docker compose -f /opt/proxcenter/app/project/docker-compose.yml \
               -f /opt/proxcenter/app/project/docker-compose.override.yml \
               down
rm -rf /opt/proxcenter/app/state/data/*        # the branding volume
```

`appctl install proxcenter` must bring the stack back and end at `changed=0`
on the run after it.

**The acceptance criterion that matters most is not the changed count.** It is
that the *stored* Proxmox connection still works after a reinstall: the
`APP_SECRET` in the guest's `.env` must be byte-identical to the one from the
first run, and the connection ProxCenter stored must still decrypt. A role
that regenerated `APP_SECRET` would pass every task-level check and break the
only thing the product is for.

**Measured values to record when it lands**, in the same table the XERJ plan
uses:

| Run | Result |
|---|---|
| first install | 26 changed, 0 failed, 67 tasks, 333 s |
| second install | 0 changed, **1 failed** — `items2dict` on a list of tuples (§10) |
| third install | 1 changed, 0 failed, 67 tasks, 588 s — the Postgres directory ownership fix |
| fourth install | **0 changed, 0 failed**, 67 tasks, 60 s |

The fourth run is the settled state. The 588 s on the third is the frontend
container restarting against a database it could finally open, and the
entrypoint re-running its migration check.

## 10. Traps this role is written around

- **The Compose file must be fetched with a checksum.** Without it,
  `get_url` re-downloads on every play and reports changed — the most common
  way a second run stops being `changed=0`.
- **`docker compose up -d` is not idempotent by itself.** It reports
  "Running" every time. The `changed_when` has to come from whether the
  image digest moved, not from the command's exit code.
- **`docker compose up` without `--pull never`** will fetch `latest` and
  defeat the digest pin in one step.
- **Two `-f` flags, or the override is ignored.** `docker compose -f a.yml -f
  b.yml up` — a single `-f` silently drops the override, and the stack runs
  the unpinned image with a green play.
- **`external: true` volumes are not created by Compose.** The upstream file
  declares both of them external. Without the override's bind mounts (or two
  explicit `docker volume create` calls) the stack does not start at all.
- **`ufw` does not filter a Docker-published port.** Docker's chain is
  evaluated before `ufw`'s `INPUT`. A firewall rule that reads as applied in
  `ufw status` enforces nothing. Measured on vmid 107.
- **The frontend container runs as uid 1001.** A bind-mounted `/app/data`
  owned by root makes the container fail to write, and the symptom is a
  permission error in the container's logs rather than a health-check
  failure.
- **The Postgres container runs as uid 70** and its entrypoint chowns an
  empty bind-mounted `PGDATA` itself. Pre-chowning it to 1001 would break
  it.
- **`APP_SECRET`, `NEXTAUTH_SECRET` and `POSTGRES_PASSWORD` are generated
  once.** Regenerating `APP_SECRET` breaks the stored Proxmox connection;
  regenerating `POSTGRES_PASSWORD` breaks the database.
- **`PROXCENTER_SETUP_TOKEN` matters when the UI is on the LAN.** The
  first-run setup endpoint is unauthenticated until the first admin account
  exists. D3=B makes this the operator's first mistake waiting to happen.
- **The Proxmox API endpoint must be the public name.** Measured from a guest
  on 2026-11-09: `https://kvm.bruj0.net:8006` completes a TLS handshake
  (the certificate's CN is `kvm.bruj0.net`, and it resolves to the public
  address); `https://10.0.0.1:8006` is reachable at the TCP level but fails
  certificate verification with `IP address mismatch`. A connection
  configured with the vnet address fails at the TLS layer with an error that
  does not name the cause.
- **`latest` and `1.4.14` currently resolve to the same digest.** That is
  convenient and temporary. Pin the digest; do not pin the tag and assume
  the two agree.

### Two traps this deployment found

Both shipped green on the first run and broke the second. Neither is visible
in a task count.

**`regex_findall` returns tuples, and `items2dict` wants dicts.** Parsing the
existing `.env` to keep its generated credentials failed with
`items2dict requires a list of dictionaries, got [('APP_SECRET', '…'), …]`.
The fix is `dict(...)` over the findall result, not `items2dict`. This is the
same family as the `next()`-twice trap in `AGENTS.md`: a Jinja filter whose
input shape is not what its name suggests.

**The Postgres bind mount must be owned by uid 70, not root.** The image's
entrypoint chowns an **empty** `PGDATA` and then drops to uid 70. On the first
run that is enough. On the second the directory is no longer empty, so the
chown is skipped — and a `root:root 0700` directory means uid 70 cannot even
traverse into it. Measured on vmid 125:

```
FATAL: could not open file "global/pg_filenode.map": Permission denied
```

with **both containers reporting `running`** and `/api/health` answering
`503 {"db":"unreachable"}`. The role now owns the directory as
`proxcenter_postgres_uid: 70`, so the entrypoint's chown is a no-op rather
than the only thing standing between a reinstall and a database that cannot
be opened.

The general lesson is the one `AGENTS.md` already states for `fchmod`: a
directory a container writes to is a capability, and the uid that must
traverse it is the container's, not root's.

## 11. What is still open

1. **The DNS record.** `proxcenter.intranet.local` in the `intranet.local`
   zone, pointing at the guest's leased address. It has to be re-pointed if
   the lease moves. The zone is served by PowerDNS at `10.0.0.3`, and the
   Proxmox SDN registers guest hostnames in it automatically — so the
   record may be created by the guest's own registration rather than by
   hand. **Unverified**: the controller could not resolve
   `xerj.intranet.local` or `proxcenter.intranet.local` on 2026-11-09,
   because the controller's resolver is not the internal one. What is
   confirmed is that a guest resolves `kvm.bruj0.net` correctly.
2. **The API token's privileges.** D6. Start with `PVEAuditor`.
3. **Whether the guest should auto-start.** The framework's default is
   `onboot: 0`, and every guest in this inventory currently has it. A
   management plane that comes up after the host reboots is the useful
   default for this particular application, and it is a one-line override in
   `inventory/group_vars/pc/main.yml`.
4. **Whether to keep the UI on plain HTTP.** D3. The reverse proxy is the
   follow-up, and it needs a hostname and a certificate.
5. **The metrics retention.** The default is 14 days. At upstream's stated
   ~90 MB per node per retention window, one node is negligible. If the
   guest is later pointed at a larger cluster, that number is the first
   thing to check against the 80 GB disk.
